# API 設計意図

このドキュメントは、各 API の処理について「なぜそう設計したか」の意図を記録します。

---

## POST /api/users - ユーザー登録

### 概要

ユーザー情報（企業名、氏名、メールアドレス、パスワード）を受け取り、新規ユーザーを作成する。

### 設計意図

#### 1. パスワードの扱い

- **ハッシュ化アルゴリズム**: Argon2 を採用
  - 理由: 最新のパスワードハッシュアルゴリズムで、サイドチャネル攻撃に強い
- **パスワード要件**: 8 文字以上、英大文字・小文字・数値・記号の 4 種のうち 3 種以上
  - 理由: セキュリティを確保しつつ、ユーザビリティを考慮した要件

#### 2. レスポンス設計

- **ステータスコード**: 201 Created
- **レスポンスボディ**: なし
  - 理由: プロトタイプ段階では、ユーザー登録後に ID を使用する API がないため。必要になったら返す設計にしている。

#### 3. メールアドレスの重複チェック

- **実装方針**: アプリ側で事前チェック + DB 制約（二重チェック）
  - 理由:
    - アプリ側で事前チェックすることで、エラーメッセージを明確にできる
    - DB 制約を最終的な防御として残すことで、並行リクエスト時の整合性も保証
    - usecase 単位でトランザクションを貼るため、トランザクション内でチェックできる

#### 4. バリデーション

- **文字数制限**:
  - companyName, name: 255 文字以内（DB スキーマの VARCHAR(255)に合わせる）
  - email: 254 文字以内（RFC 5321 準拠。メールアドレス全体の最大長は 254 文字）
  - 理由: PostgreSQL を採用しており、DB スキーマで VARCHAR(255)と定義されているため、アプリ側でも制限をかける。ただし、email については RFC 5321 に準拠し、254 文字を上限とする
- **企業名の重複**: 許可（重複 OK）
  - 理由: 同じ企業名の異なるユーザーが存在する可能性があるため

#### 5. トランザクション管理

- **スコープ**: usecase 単位でトランザクションを貼る
  - 理由: Java の Spring Framework を使用するため、`@Transactional`を usecase クラスに付与する方針

#### 6. エラーレスポンス

- **400 Bad Request**: バリデーションエラー（プロパティ毎のエラー詳細を`details`配列で返す）
- **409 Conflict**: メールアドレスが既に存在する場合
  - 理由: リソースの競合を明確に示すため

## POST /api/auth/login - ログイン

### 概要

メールアドレスとパスワードによる認証を行い、成功時に JWT アクセストークンを発行する。

### 設計意図

#### 1. 認証方式

- **認証方法**: メールアドレスとパスワードによる認証
- **トークン発行**: 認証成功時に JWT アクセストークンを発行
  - 理由: ステートレスな認証により、スケーラビリティが高い

#### 2. JWT トークンの仕様

- **有効期限**: 24 時間
  - 理由: プロトタイプ段階でリフレッシュトークンを設計しないため、1 日 1 回のログインで済む実用的な設定
- **リフレッシュトークン**: 設計しない
  - 理由: プロトタイプ段階のため、シンプルな設計を優先
- **ペイロード**: userId のみを含める
  - 理由: ユーザーの特定ができれば十分なため

#### 3. パスワード検証

- **検証方法**: Argon2 でハッシュ化されたパスワードを、登録時と同じ Argon2 ライブラリで検証
  - 理由: ユーザー登録時と同じアルゴリズムで一貫性を保つ

#### 4. バリデーション

- **email 形式チェック**: 実装する
  - 理由: ユーザビリティを考慮し、メール形式エラーを早期に検知できるようにする
- **その他のバリデーション**: 必須フィールドのチェック

#### 5. エラーハンドリング

- **401 Unauthorized**: すべての認証失敗ケースに対して統一して返す
  - 理由: セキュリティ上の理由により、メール形式エラー、パスワード形式エラー、認証情報不一致など、すべての認証失敗ケースに対して同一の 401 レスポンスを返す。攻撃者にどの情報が正しく、どの情報が間違っているかを推測させないため。
- **400 Bad Request**: バリデーションエラー（プロパティ毎のエラー詳細を`details`配列で返す）
  - 理由: email 形式チェックは 400 で返し、認証処理に進む前のバリデーションエラーとして扱う

#### 6. セキュリティ対策

- **レート制限**: 実装しない
  - 理由: プロトタイプ段階のため。また、今回の要件ではユーザー情報変更やパスワード忘れ時のルートがないため

#### 7. トランザクション管理

- **スコープ**: usecase 単位でトランザクションを貼る
  - 理由: ユーザー情報の読み取り処理でも、トランザクション内で一貫性を保つため

## GET /api/invoices - 請求書一覧取得

### 概要

指定期間内に支払いが発生する請求書データの一覧を取得する。ログインユーザーの請求書のみを取得する。

### 設計意図

#### 1. 認証・認可

- **対象ユーザー**: ログインユーザー（JWT の userId）の請求書のみを取得
  - 理由: ユーザーは自身の請求書のみを確認できるべき。セキュリティ上の理由から、他のユーザーの請求書は取得できないようにする

#### 2. レスポンスに含めるフィールド

- **基本フィールド**: id（請求書 ID）、issueDate（発行日）、paymentDueDate（支払期日）、totalAmount（請求金額）
  - 理由: プロトタイプ＋一覧なので、詳細情報はノイズ。期限と金額、発行日があれば一覧として十分。id は請求書を識別するために必要。プロトタイプには支払先情報は含まれないため、companyName は不要。税率などを見たい場合は、詳細 API を作って、そっちに持つべき。
- **将来の拡張性**: 将来的に invoices テーブルに支払先情報（支払先 ID や支払先マスタテーブルなど）を追加することを考慮している。その場合は、レスポンスに支払先情報を含めることも可能
- **ページネーション情報**: page_number、page_size、total、total_pages
  - 理由: 一覧取得ではページネーションが必要なため
- **空の結果セット**: 該当データがない場合は空配列 `[]` とページネーション情報（total: 0）を返す

#### 3. クエリパラメータ

- **paymentDueFrom / paymentDueTo**: 任意パラメータ
  - 理由: 期間指定は任意だが、デフォルト値を持たせる（後述の提案参照）
- **page_number**: ページ番号（デフォルト: 1）
  - 理由: ページネーションのため
- **page_size**: 1 ページあたりの件数（デフォルト: 20、最大: 100）
  - 理由: パフォーマンスとユーザビリティのバランスを考慮

#### 4. クエリパラメータのデフォルト値（提案）

- **paymentDueFrom**: 未指定時は「今日」をデフォルトとする
  - 理由: 要件「未来の支払期日の請求書データ」を考慮し、過去の請求書は表示しない。ユーザーは「これから支払うべき請求書」を確認したいため
- **paymentDueTo**: 未指定時は「1 ヶ月後」をデフォルトとする
  - 理由: 要件「現金の支出を最大一ヶ月遅らせることができる」を考慮し、1 ヶ月先までの請求書を表示するのが自然
- **両方未指定の場合**: 今日から 1 ヶ月後までの期間で取得
- **片方のみ指定の場合**: 指定された方のみを適用し、もう一方はデフォルト値を使用

#### 5. ソート順

- **デフォルトソート**: 支払期日（paymentDueDate）の昇順、同じ支払期日の場合は発行日（issueDate）が早い順
  - 理由: ユーザーは「次に支払うべき請求書」を優先的に確認したいため、期日が近い順に表示する。同じ期日の場合は発行日が早い順で順序を保証する
- **ソート順の指定**: プロトタイプ段階では固定。将来的にはソート順の指定（昇順/降順、複数カラム）があってもよいが、現時点では不要

#### 6. ページネーション

- **実装**: 必須
  - 理由: そんな数千件とかもいかないと思うが、パフォーマンス考慮。そもそもそのデータを使ってフロント表示とかあったらフロントが困る
- **形式**: page_number/page_size 形式を採用（OFFSET/LIMIT ベース）
  - 理由: パラメータ名が明確で、RESTful API で一般的な形式。実装がシンプル
- **OFFSET/LIMIT を採用する理由**:
  - 前提として一覧取得対象のデータ量は限定的（指定期間内に支払いが発生する請求書データの一覧＝支払い済みは含まれないため）
  - 要件上、「支払いが発生する」ものだけを取得するため、支払い済みデータは別テーブルに移動させる設計を想定（支払い済み一覧的な）
  - データ量が限定的なため、OFFSET/LIMIT でもパフォーマンス上の問題は発生しにくい
  - インデックス（user_id, payment_due_date）を適切に設定することで、十分に高速なクエリが可能

#### 7. トランザクション管理

- **スコープ**: usecase 単位でトランザクションを貼る
  - 理由: 読み取り処理でも、トランザクション内で一貫性を保つため

#### 8. エラーレスポンス

- **400 Bad Request**: バリデーションエラー（日付形式エラー、ページ番号が 0 以下、日付範囲の論理エラー（paymentDueFrom > paymentDueTo）など）
- **401 Unauthorized**: 認証エラー（JWT トークンが無効、期限切れなど）

## POST /api/invoices - 請求書登録

### 概要

新しい請求書データを作成する。JWT による認証が必要。

### 設計意図

#### 1. リクエストパラメータ

- **必須パラメータ**: issueDate（発行日）、paymentAmount（支払金額）、paymentDueDate（支払期日）
  - 理由: 請求書登録に必要な最小限の情報。発行日と登録日は異なるため、発行日をリクエストボディで受け取る
- **user_id**: JWT から取得
  - 理由: セキュリティ上の理由から、リクエストボディに含めず、JWT から取得する

#### 2. 請求金額の計算ロジック

- **計算式**: `支払金額`に手数料 4%を加えたものに、さらに手数料の消費税 10%を加えたもの
  - `fee_rate = 0.04`（4%）
  - `tax_rate = 0.10`（10%）
  - `fee = payment_amount * fee_rate`
  - `tax_amount = fee * tax_rate`
  - `total_amount = payment_amount + fee + tax_amount`
  - 例: 支払金額 `10,000` の場合、請求金額は `10,000 + (10,000 * 0.04 * 1.10) = 10,440`
- **端数処理**: 四捨五入（`RoundingMode.HALF_UP`）を採用
  - 理由: 決済代行サービスとして、顧客と企業のどちらにも偏らない公平性を重視するため。業界標準として広く採用されている方法であり、透明性と信頼性を確保できる。計算過程で小数点以下 3 桁以上が発生した場合、小数点以下 2 桁に四捨五入して保存する
- **理由**: 要件に基づく自動計算。手数料と消費税を DB に保存するため、fee、fee_rate、tax_amount、tax_rate も保存する

#### 3. バリデーション

- **発行日（issueDate）**: 過去または今日のみ許可（未来は不可）
  - 理由: 一般的に、請求書の発行日は既に発行済みの請求書を登録する場合が想定されるため、過去または今日のみ許可
- **支払期日（paymentDueDate）**: 未来の日付のみ許可
  - 理由: 要件「未来の支払期日の請求書データ」に基づく
- **支払金額（paymentAmount）**: 正の値のみ許可（0.01 以上）、小数点以下 2 桁まで許容
  - 理由: 請求書の支払金額は正の値である必要があるため。日本の一般的な請求書では支払金額が小数点以下になることは稀だが、時間単位のサービスや重量単位の販売などで小数点以下が発生する可能性があるため、システムとしては小数点以下 2 桁まで許容する設計とする

#### 4. レスポンス設計

- **ステータスコード**: 201 Created
- **レスポンスボディ**: id（請求書 ID）を含める
  - 理由: RESTful API の一般的な設計。クライアントが追加の GET リクエストなしで ID を取得でき、登録後の処理（詳細表示など）に利用できる。詳細 API は現時点では存在しないが、将来的に作成する可能性を考慮

#### 5. トランザクション管理

- **スコープ**: usecase 単位でトランザクションを貼る
  - 理由: 請求書登録処理では、複数の計算と DB への保存が行われるため、トランザクション内で一貫性を保つ

#### 6. エラーレスポンス

- **400 Bad Request**: バリデーションエラー（日付形式エラー、発行日が未来、支払期日が過去または今日、支払金額が 0 以下など）
- **401 Unauthorized**: 認証エラー（JWT トークンが無効、期限切れなど）
